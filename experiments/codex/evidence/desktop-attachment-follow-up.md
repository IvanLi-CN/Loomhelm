The current version and configuration have no proven official hot-attach method for the existing desktop app-server. This is a current evidence boundary, not a claim that future versions can never support one; the wrapper candidate is a separate launch-time experiment rather than a hot-attach mechanism.

## Ranked experiment recommendation

The practical order is wrapper first, shared daemon second, and forced WebSocket or SSH proxy third. The wrapper has the strongest local entry evidence because the current bundle accepts an absolute executable override while preserving the desktop's generated argv and environment; it remains an unsupported private hook and has not been tested. The shared-daemon path is still worth a later controlled comparison because the selector remains packaged and [#31991](https://github.com/openai/codex/issues/31991) records an older user-observed topology, but the observed nonempty `getConfigOverrides()` result from the `codex_app` plugin is sufficient to block this startup's branch. `CODEX_CLI_PATH` is a separate parent-environment condition; the observed child value must not be used to infer that parent condition. Forced WebSocket and SSH proxy are transport mechanisms for an existing endpoint, not evidence that the current desktop owner is externally attachable.

If the shared-daemon or explicit Unix-socket candidate is tested, the Go Connector must dial the Unix socket and complete the WebSocket HTTP Upgrade handshake. It must not write JSONL directly to the socket. A child `codex app-server proxy --sock <path>` is the alternative that converts the socket transport to stdio JSONL for a Connector process; both choices still require an endpoint that already exists.

The first wrapper phase is an independent disposable proxy simulation or isolated process check with no Desktop restart and no startup replacement. It must validate JSON-RPC framing, request-ID routing, notification ordering, ordinary approval first-response arbitration, denial, interrupt, and bridge reconnect without claiming same-desktop acceptance. After that phase passes, prepare separate reviewable launch and rollback scripts using scoped `CODEX_CLI_PATH=<wrapper>` and `CODEX_APP_SERVER_FORCE_CLI=1`; apply them only after the owner explicitly confirms the affected application scope and an idle window. The current R01 authorization does not cover restarting the whole Desktop application while other tasks are active. If later approved, the wrapper must spawn exactly one pinned bundled `codex app-server` child, preserve the received argv/env including `CODEX_APP_TOOLS_PIPE_PATH` and every `mcp_servers.codex_app` override, and expose only a mode-0600 local Unix socket to the Loomhelm bridge. The bridge must be a protocol-aware logical second client of that same child, not an independent app-server.

The proxy must namespace and rewrite request IDs, preserve notification ordering, and arbitrate ordinary approval responses with first-valid-response-wins semantics. Late duplicate responses must be rejected or ignored. `userVerification` must stay desktop-owner-only and be reported as unavailable to the bridge. Bridge disconnect must not kill the child; child exit must fail pending work and create a new generation rather than silently spawning a replacement. A reconnect to the same live child can be tested; a restart or independent `thread/resume` is a cold-resume control and does not establish same-instance attachment.

The test gate is exact child PID plus exact thread/turn identity observed by both desktop and bridge, followed by the fixed approval, denial, interrupt, streamed-event, and bridge-reconnect scenarios. The test thread must be created after the wrapper child is observed, so any later approved startup replacement is separated from the live same-child control phase. Roll back by restoring the normal Desktop startup environment and verifying that only the test wrapper process and socket have exited; do not close, signal, or clean up other normal Desktop app-servers or active tasks.
