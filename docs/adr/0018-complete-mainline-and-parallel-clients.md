# ADR 0018：完整主干与并存的客户端实现

## 状态

已接受。

## 背景

完整工程长期由 `feat/phase1` 承载，默认分支 `main` 与其分叉；新增 TS 客户端在缺少完整工程的 main 上交付。这使默认分支不能代表可开发、可验证的完整项目，也使客户端新增需求被误解为替换既有 Go 实现。

## 决策

`main` 是唯一默认集成主干，必须包含服务端、Go 客户端、Web App 与独立 TS 客户端。使用保留双方祖先的普通合并汇入历史，不重写已发表提交。`feat/phase1` 保留历史身份，不再作为新功能或发布操作的默认来源。

产品端名称仍只有服务端、客户端、Web App。Go 与 TypeScript 是客户端的两种实现；Go 程序保持既有入口、协议、状态和发行方式，TS 实现独立放在 `clients/typescript/`，其运行时合同见 [ADR 0017](0017-typescript-client-runtime.md)。新增 TS 实现不要求服务端或 Web App 在线，也不替换 Go 实现。

根 Bun workspace 保留原有 Web 与共享包；TS 包独立管理 npm 依赖并支持 Node.js/Bun 验证，通过统一检查入口接入工程 CI。验证覆盖 PR 与 main，发布和部署仍需显式操作及授权。

## 取舍

保留历史可以证明完整工程与客户端贡献均进入新主干，并保存原有 PR 的溯源关系；代价是审查中包含较大的历史合流和明确的文档冲突处理。独立 npm 包保持 TS 客户端无需 Web 工具链即可安装，代价是工程维护两个边界清楚的依赖安装入口。

## 验收边界

从 main 的干净克隆必须能够定位和验证完整工程与两种客户端。仓库完整、构建通过与一期产品业务验收是独立结论；Connected mode、真实 Codex 联调和历史未完成的业务验收不得仅凭历史合流或模拟测试宣称完成。原始验收记录和提交身份保持其原意。
