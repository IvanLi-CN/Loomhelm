# Codex compatibility research

## Scope

This research records host-local control-path evidence for `REQ-LH-002` and `REQ-LH-003`. It does not define a product adapter or claim support for existing desktop-session control without same-instance evidence.

## Official protocol baseline

OpenAI Docs document Codex app-server as a bidirectional JSON-RPC interface with `stdio://` JSONL, Unix-socket WebSocket, and experimental WebSocket transports. The same documentation defines `thread/start`, `turn/start`, streamed item events, approval request callbacks, and `turn/interrupt`; it also states that app-server and WebSocket transport are experimental and intended primarily for development/debugging. See [Codex App Server](https://learn.chatgpt.com/docs/app-server) and [Codex CLI reference](https://learn.chatgpt.com/docs/cli/reference).

The official model page confirms that `gpt-5.6-luna` supports reasoning effort `max`; the local app-server `model/list` response independently returned that model and effort. See [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna).

## Host facts

The host has Homebrew `codex-cli 0.162.1` and the ChatGPT desktop embedded CLI `codex-cli 0.163.0-alpha.10.2`. The desktop application runs an embedded app-server process, but its local Unix endpoints are anonymous IPC channels owned by the desktop process; no path-addressable app-server listener was found through the documented managed control socket.

The documented managed control socket was absent initially. A temporary `codex remote-control start --json` created a managed daemon running app-server `0.163.0` and a local socket, but `codex remote-control pair --json` returned `remote control pairing is unavailable until enrollment completes`. This proves daemon startup, not remote enrollment or desktop-thread sharing. The temporary daemon was stopped after probing, and its process and managed socket were verified absent; no global configuration or authentication state was changed.

## New-session result

The desktop-embedded CLI started as a separate host-local `codex app-server --listen stdio://` process in `/private/tmp/loomhelm-r01-codex-test`. The probe completed `initialize`, `model/list`, `thread/start`, and `turn/start` with `model=gpt-5.6-luna` and `effort=max`; it observed a real `thread/started`, `turn/started`, streamed `item/agentMessage/delta`, and `turn/completed` with status `completed`. The event evidence stores only stable hashes of thread/session/turn identifiers.

This establishes the selected-host new-session protocol path for the current CLI build. It does not establish that a Connector can attach to an existing desktop process or that a thread created by an independent app-server is the same live desktop instance.

The companion control probe also passed on the new-session path: it observed a real approval request and accepted harmless command, a declined harmless command, an interrupted long-running command, then a fresh app-server connection resuming the same thread and reconciling three persisted turns. The redacted run summary is [host-control-summary.md](../../experiments/codex/evidence/host-control-summary.md); the full summary can be regenerated into a disposable path with `control-probe.mjs`.

## Existing desktop-session result

The owner authorized one disposable desktop target, `Loomhelm R01`, with a projectless Codex thread and the fixed `gpt-5.6-luna/max` model. The redacted target reference is `thread-bd8358fda03363e67e`; its initialization turn is `turn-f8f1497b700c04cb74`, which completed with the fixed marker `R01_DESKTOP_TEST_READY`.

The native Codex app bridge then sent the fixed no-tool prompt `Reply with exactly R01_DESKTOP_BRIDGE_OK and do not use tools.` to that target and read the resulting `turn-617e4cdac2ddcc2316`, which completed with `R01_DESKTOP_BRIDGE_OK`. This proves that the app-internal bridge can target the designated thread, create a new turn, and read its result. The bridge is preparation evidence only: it is a Codex app capability, not a path-addressable host Connector endpoint that Loomhelm can reuse.

External control of the existing desktop session is still not proven. The documented managed daemon is not enrolled for pairing, the desktop app's embedded app-server is not exposed at the documented control socket, and no reusable host connection can currently attach to the same live desktop thread/turn. Approval, denial, interrupt, disconnect/restart reconciliation, and live event streaming therefore remain unverified on the external path. The redacted native-bridge preparation card is [desktop-bridge-summary.md](../../experiments/codex/evidence/desktop-bridge-summary.md).

The current acceptance state is `blocked` for the currently observed external path, but this is not a conclusion that every bridge design is infeasible. An independent app-server cold resume, including `thread/read` or `thread/resume` against a different process, is not same-instance evidence; a warm resume on the same app-server process can be valid when it reuses the live conversation and preserves pending request ownership. The stable `v0.163.0` upstream source reviewed by the parent task records this distinction in `thread_state.rs`, `thread_lifecycle.rs`, and `outgoing_message.rs` at [commit 83086188](https://github.com/openai/codex/commit/83086188ae0614bd882818ff1aa23f3194962012). The same source shows that an ordinary approval callback is consumed by the first valid response, while `userVerification` remains owner-bound and must not be promised as remotely answerable. Do not mark `REQ-LH-002` or `VER-LH-002` passed until the same app-server process, thread and turn identities are observed across a reusable control path and the required approval/interrupt/restart reconciliation scenarios complete.

## Bounded attachment follow-up

The installed desktop CLI `0.163.0-alpha.10.2` exposes `app-server proxy --sock <path>`, `codex --remote unix://PATH|ws://...`, and `codex queue --thread <UUID> --remote <endpoint>`. These are client/transport entry points for an app-server endpoint that already exists; they are not discovery or attachment mechanisms. The documented `app-server --listen` transport applies to an app-server process launched with that listener, and the current desktop invocation does not expose that listener. `queue` only submits a message and does not by itself provide approval, interrupt, event-stream or restart-reconciliation control.

The same CLI exposes `app-server daemon enable-remote-control`, which changes remote-control behavior for future starts and a currently running managed daemon, plus `remote-control pair`, which requires an enrolled managed remote-control server. These operations were not run in this follow-up because they change global/managed state and can require pairing or identity participation; the earlier bounded probe already observed pairing failure with enrollment incomplete.

Read-only inspection of the live desktop process found the embedded app-server command running without a `--listen` endpoint. Its Unix descriptors were anonymous process-owned connections, no path-addressable Unix socket or TCP listener was present, the managed control socket was absent, and both `app-server daemon version` and `app-server proxy --sock /Users/ivan/.codex/app-server-control/app-server-control.sock` failed because the socket did not exist. This exhausts the currently observable local entry points without changing state.

The official [Remote connections](https://learn.chatgpt.com/docs/remote-connections) page documents a first-party Settings > Connections flow with QR/account/workspace pairing, a secure relay, and prompts, approvals and follow-up messages sent to a connected host. It does not document a third-party Connector endpoint, app-server URI, thread/turn RPC, or Connector authentication contract, so that first-party workflow is not evidence for Loomhelm's Go Connector. The current version and configuration therefore have no proven official hot-attach method for the existing desktop app-server. This does not prove that future versions can never support one; the unresolved item is whether OpenAI will document a third-party endpoint or a desktop startup integration that preserves the same live thread identity. Until such evidence exists, the existing-desktop acceptance remains `blocked`.

## Current desktop bundle evidence

The local ChatGPT bundle is `26.1013.31256` build `20586`; its embedded CLI reports `codex-cli 0.163.0-alpha.10.2`. The inspected app.asar digest is `bf9c41fa9770fbfacfba93042ff71c24cb65c82935819377275faac08103383f`; the embedded CLI digest is `1afb28c01d7d49e892bd75f11076b10f1451e34e0ee308a95e5ab7f69f9c84fe`. These hashes identify the inspected artifacts and are not a claim that the bundle is an official source release.

The packaged source in `.vite/build/application-network-startup-DB1VeU3v.js` still contains a local-daemon branch, but it is guarded by all of the following: no `getConfigOverrides()` result, local host, `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1`, no `CODEX_APP_SERVER_FORCE_CLI=1`, no `CODEX_CLI_PATH`, no host CLI override, no bundled Git override, and a successful `app-server daemon version` compatibility check. The same source connects that branch to `ws://localhost/rpc` over `app-server-control.sock`; otherwise it constructs a private stdio transport.

The live desktop child (PID `10095`) currently runs the bundled CLI as `app-server` without `--listen`, with `-c plugins.codex-app-tools@openai-bundled.mcp_servers.codex_app.enabled=true` and the code-review override. Its environment has `CODEX_CLI_PATH` set to the bundled CLI and `CODEX_APP_TOOLS_PIPE_PATH` set, while `CODEX_APP_SERVER_USE_LOCAL_DAEMON`, `CODEX_APP_SERVER_FORCE_CLI`, and `CODEX_APP_SERVER_WS_URL` are not set. The child observation does not establish the Electron parent's `process.env`; the nonempty plugin/config override is independently sufficient to fail the local-daemon branch. The managed control socket is absent, and the child has anonymous Unix descriptors rather than a path-addressable app-server listener. This is a live observation only; the process was not restarted or signaled.

The packaged source in `.vite/build/main-CLu1A25j.js` accepts an absolute `CODEX_CLI_PATH` when it resolves a local executable: the path only needs to exist as a regular file, after which the generated app-server argv is passed to that executable. The generated environment is based on the desktop environment, and the app-tools pipe path is part of that environment. The same file reads the bundled `codex-app-tools/.mcp.json` when `CODEX_APP_TOOLS_PIPE_PATH` is available and emits `mcp_servers.codex_app` request-level overrides. This means a wrapper entry is statically plausible and can preserve the plugin override and pipe by forwarding argv and env, but it does not prove that a second logical client can safely share one stdio stream.

The same packaged source contains the SSH transport bootstrap. It checks `CODEX_SSH_SKIP_APP_SERVER_BOOT=true` before starting a remote `codex app-server --listen unix://`, then runs remote `codex app-server proxy` over SSH. This is a concrete proxy path for an existing managed remote Unix-socket daemon; it does not attach to the current desktop child, whose transport is private stdio. The environment variable is present in the current desktop bundle, but it is not a documented third-party attachment contract.

## Ranked bridge experiments

The local evidence gives the following order for a controlled experiment, not a production support claim.

| Rank | Candidate | Current evidence | Main blocker or risk |
| - | - | - | - |
| 1 | Launch wrapper around the desktop's bundled CLI | Absolute `CODEX_CLI_PATH` is accepted by the bundle; generated argv includes the desktop plugin overrides; generated env includes the app-tools pipe | A single stdio stream has one physical app-server client, so the wrapper must virtualize request IDs, notifications, and server callbacks without creating a second app-server runtime |
| 2 | Shared managed Unix daemon | The bundle still contains the `CODEX_APP_SERVER_USE_LOCAL_DAEMON` branch and the documented socket transport; issue [#31991](https://github.com/openai/codex/issues/31991) records an older working user setup | The observed nonempty `getConfigOverrides()` result from the `codex_app` plugin is sufficient to make the branch unreachable in this startup; `CODEX_CLI_PATH` is a separate parent-environment condition and the child value does not prove the parent value. Issue [#41014](https://github.com/openai/codex/issues/41014) remains an open user report as of 2026-10-14 with no maintainer fix commitment |
| 3 | `CODEX_APP_SERVER_WS_URL` or SSH proxy | The bundle has both the external WebSocket routing hook and the SSH `app-server proxy` path; official docs describe Unix sockets as WebSocket-over-HTTP-Upgrade transports | The external endpoint is not an official same-desktop attach contract; issue #41014 includes a user report of `invalid transport in mcp_servers.codex_app`, and SSH proxy still needs an already running managed endpoint |

The three issue pages are evidence of user-observed behavior, not official support guarantees. [#31991](https://github.com/openai/codex/issues/31991) reports a shared-daemon topology on an older CLI/Desktop pair; [#41014](https://github.com/openai/codex/issues/41014) reports the later override regression and remained open after its 2026-10-14 update; [#40134](https://github.com/openai/codex/issues/40134) remains an open request for a documented Desktop-to-external-App-Server contract. The public CLI/App Server source and docs establish explicit transports, not a hot-attach API for an already running private Desktop stdio owner.

For the shared-daemon or explicit Unix-socket candidate, the Go Connector must treat the socket as a WebSocket-over-HTTP-Upgrade transport, not as a raw JSONL stream. The implementation choices are a Unix dial followed by the documented WebSocket handshake, or a child `codex app-server proxy --sock <path>` process whose stdio is then consumed as JSONL. Neither choice discovers or attaches to a private stdio owner by itself.

## Minimal wrapper PoC

This was the smallest proposed next experiment. Its isolated phase is now implemented as a standard-library-only Go proxy prototype and validated against a controlled mock child; the Desktop integration phase remains intentionally unexecuted and must run only against the owner-designated disposable R01 desktop target with the already authorized fixed printf, sleep30, approval-deny, and interrupt/reconnect scenarios.

1. Pin the exact bundled CLI path and digest before launch. Prepare a user-owned executable wrapper outside the repository that never reads `CODEX_CLI_PATH` as its child path, so it cannot recurse; it must point to the pinned bundled CLI and fail closed if the digest or version changes.
2. The isolated proxy phase is validated without restarting ChatGPT Desktop or replacing its launch environment. Its fixture tests exercise JSONL framing, request-ID mapping, notification fan-out, ordinary approval first-response arbitration, duplicate-response suppression, owner-bound callback routing, child signal/exit handling, bounded bridge backpressure, and bridge reconnect. A retained follow-up also exercised the exact current bundled CLI through the wrapper, including model discovery, same-thread event fan-out, real approval accept/decline, bridge disconnect/reconnect, `turn/steer`, and `turn/interrupt`; this remains a new isolated app-server proof and cannot pass same-desktop acceptance.
3. The isolated phase produced a reviewable launch script and a separate rollback script. The proposed launch environment is scoped `CODEX_CLI_PATH=<wrapper>` and `CODEX_APP_SERVER_FORCE_CLI=1`; the first selects the wrapper executable and the second suppresses automatic WebSocket/SSH routing and the local-daemon branch. Do not apply either script until the owner explicitly confirms the affected application scope and an idle window; the existing R01 authorization does not authorize restarting the whole Desktop application or replacing its startup while other tasks are active.
4. If and only if that later approval is given, the wrapper spawns exactly one bundled `codex app-server` child with the received argv and a verbatim environment, including `CODEX_APP_TOOLS_PIPE_PATH`, the desktop plugin variables, and every `mcp_servers.codex_app` `-c` override. It owns a mode-0600 local Unix control socket for the Loomhelm bridge and records only redacted child PID, CLI version, argv digest, and environment-key presence.
5. Keep the desktop's stdin/stdout channel as the physical child channel. The bridge side connects to the wrapper socket as a logical second client; the proxy must not start `codex app-server` again, use `thread/resume` against another process, or expose a public listener.
6. Give each logical client a request-ID namespace and map `(client, request_id)` to one child request ID. Fan out notifications in order. For ordinary approval requests, accept exactly the first valid response, cancel the other pending callback mapping, and record late responses as rejected/ignored without forwarding them. Route owner-bound `userVerification` only to the desktop client and surface it to the bridge as unavailable for remote response.
7. On bridge disconnect, fail only that client's pending requests and keep the child and desktop stream alive. On child exit, fail every pending request and expose a new generation; do not silently start a replacement child because that would invalidate same-process evidence. A bridge reconnect to the same live child may reinitialize its logical session, but a child restart is a new candidate and requires a fresh thread/turn identity check.
8. Start the fixed desktop test thread only after the wrapper child is observed. The retained isolated probe now proves the exact thread and turn identifiers, child PID, streamed event ordering, approval first-response behavior, denial, interrupt, and bridge reconnect reconciliation against the current bundled CLI. A later Desktop phase would still need to prove those same properties after the wrapper becomes the Desktop startup executable; a persisted thread observed through a different process is a cold-resume control and does not pass this gate.
9. Roll back by restoring the normal Desktop startup environment and verifying that the test wrapper process and its control socket have exited. Do not close, signal, or clean up any other normal Desktop app-server or active task; record only the test wrapper/child exit status and socket absence.

The wrapper experiment has three independent gates: executable selection and argv/env preservation; protocol multiplexing without duplicate side effects; and same-child thread/turn evidence. The mock-child fixture covers the mechanics gate, while the retained real-CLI probe covers same-child thread/turn behavior for the current bundled CLI; neither proves the live Desktop startup or that every approval or identity challenge can be controlled remotely.

## Isolated Go proxy result

## Evidence handling

Evidence should be generated into a disposable path with `new-session-probe.mjs --evidence <path>` or `control-probe.mjs --evidence <path>`. Do not commit raw app-server transcripts, rollout files, session databases, access tokens, pairing codes, or complete user messages. A valid evidence card must identify the candidate SHA, acceptance contract digest, scenario-set digest, and inspectable redacted evidence locator.
