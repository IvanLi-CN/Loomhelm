# Multi-task flow

Use for an owner-approved multi-conversation flow with explicit task dependencies. This Skill has its own input contract and runtime lifecycle; it is independent from `$dev-plan` and does not migrate or modify existing runs. Initialization is a mutating runtime action: do not invoke this Skill for read-only review, diagnosis, code exploration, or plan-only work. The main Agent creates and manages peer group and task conversations as needed. The group Agent owns its parent PR and child PR acceptance; the task Agent owns its subtask and follow PRs. The main Agent schedules; it accepts child PRs only for its own bootstrap delivery unit.

Each run may contain one `bootstrap` delivery unit followed by zero or more `regular` delivery units. Bootstrap is the only main-owned unit: the bound main conversation may commit the initial SPEC/ADR/plan documents and manage the first parent PR. It uses `owner_kind: "main"`, has no group conversation binding, and must be first. Regular units retain the group-owned contract and require an independent group conversation before activation. Parent PRs are serial by default; regular units may run in parallel only when dependencies allow it. Delivery-unit kind, ownership and group conversation binding cannot be rewritten through ordinary group updates or plan revisions. This release provides no in-place ownership-transfer command; an existing run retains its current ownership. Initialize the planned bootstrap before publishing its parent PR, then record workspace and publication receipts in the same main-owned workspace.

This remains an active top-level flow for dependency-driven delivery. An approved run requires at least two task nodes when its topology claims multiple tasks, and the authoritative runtime ledger is the source of truth for task, group, dependency, and closeout state.

## Intent and delivery contract

When the owner explicitly asks to do task orchestration with this Skill, the default intent is to create or continue a formal run and deliver its dashboard. Do not silently downgrade that request to a proposal-only Markdown artifact. Use `proposal` only for explicit review, diagnosis, or plan-only requests. The four lifecycle stages are `proposal`, `initialized run`, `scheduled run`, and `completed run`.

The first delivery is complete only when the authoritative ledger exists under `~/.local/share/multi-task-flow/data/runs/<run-id>/`, the run is bound to the current main conversation, the dependency graph is present, and the dashboard is opened using the Dashboard browser route showing the current revision. Markdown, Mermaid, and candidate `init-input.json` files are supporting inputs, never substitutes for the ledger or dashboard.

Local initialization and dashboard access do not authorize task dispatch, conversation creation, Git push, PR, merge, release, or deploy. Keep tasks `planned` until those actions receive separate authorization. Use `init`, `service ensure`, `service login`, and the host browser route below in that order. Keep the page open: SSE and heartbeat updates expose later revisions without normal re-navigation; navigate again only for connection or session recovery.

If initialization, viewer ensure/login, or browser delivery fails, report the failed stage, exact result, and blocker. Never describe a proposal as an initialized or completed run. Continue an unfinished run already bound to the main conversation; if ownership is uncertain, pause before mutation. Record the run ID, revision, owner thread ID, and dashboard entry in the conversation.

## Dashboard browser route

For dashboard delivery and inspection, first inspect the current host's exposed browser capabilities. When running in ChatGPT Desktop or Codex Desktop, default to that host's available built-in browser. This dashboard-specific route takes precedence over the generic `$ego-browser` preference; it does not change the route for unrelated browser tasks. Read the exposed tool documentation and use its supported browser selection/opening interface rather than assuming a product name, browser ID or tool name proves availability.

Open the single-use `service login` URL in that browser, then verify the intended run ID and current ledger revision from the rendered page. Keep the authenticated page open for updates. A successful open-tool response alone does not complete dashboard delivery. Protect the login URL as a credential.

If the host exposes no usable built-in browser, record the missing capability and follow the permitted `$ego-browser` route. An opening or login failure requires diagnosis before fallback; do not silently switch browsers or reuse a consumed/expired login ticket. Obtain a fresh ticket for an authorized retry. Any Chrome or Computer Use escalation still follows `$gui-escalation-gate`, and real-program screenshots still require explicit target and scope approval. If no permitted browser can render the dashboard, report the browser-delivery blocker and stable run URL without claiming delivery succeeded.

Task agents may invoke `$fast-flow` for their own direct PR, while the parent coordinator retains the graph, ledger, parent PR, and group closeout responsibilities.

Read `<skill>/../../skills/docs/vendor/dot-codex/specs/multi-task-flow/SPEC.md` and `<skill>/../../skills/docs/vendor/dot-codex/design/multi-task-flow/{orchestration,execution,data-and-scripts,web-template,plan-revision-and-change-audit}.md` in the dot-codex source installation for the model, contracts, and presentation requirements, not similarly named files in the target project. Use the installed Skill directory as `<skill>` in commands, never the candidate checkout unless explicitly testing it. Install dependencies with `bun install --frozen-lockfile` and build the local assets with `bun --no-install run build` from `<skill>`. Formal runs live at `~/.local/share/multi-task-flow/data/runs/`, independently of the Skill installation and `CODEX_HOME`. Read `references/shared-viewer.md` before viewer use or maintenance. ## Plan and schedule

Model atomic tasks and their predecessors first; each atomic task is indivisible for scheduling. Group sequential atoms into subtasks, then validate both graphs and explicit handoff facts. Plan one or more parent PR groups, group-specific post-merge release, deployment and verification tasks, and estimated intervals with sources and confidence. Default to three concurrent running tasks; waiting and blocked tasks release capacity. The owner approves the plan and any external actions with their exact targets. Do not infer dependency from group ordering or file overlap.

Use the Bun CLI with one JSON object on stdin: `bun --no-install run <skill>/scripts/orchestrate.ts <command> --input -`. Its schema is in `scripts/schema.ts`; the complete command and envelope contract is in the data design document. `init` is an owner-approved mutating command that binds the repository and the main conversation to a new run. It accepts only unbound `planned` groups/tasks and writes the initial ledger; it does not create group or task conversations. `migrate` is the only explicit schema v1 or schema v2/contract 1 to schema v2/contract 2 write path: it requires the bound main actor, exact run ID, request ID and expected revision, retains a complete backup, increments the ledger revision with its request record, and is idempotent only for identical canonical input. Read-only review, diagnosis, and planning must use source inspection or `show`/`view` and must not call `init` or a native conversation-creation tool. `show` reads a consistent snapshot. For each mutation supply a unique `request_id`, the current `expected_revision`, the bound actor and command payload. On conflict read the ledger and reconsider; replay the identical request ID only for the identical operation. Do not edit the ledger JSON manually. Agent-authored Markdown requirements are ordinary files under the run's `requirements/`.

### Phase-aware plan revisions

The runtime contract in `scripts/schema.ts` and its projection in `scripts/contract.ts` are authoritative for plan revision semantics. The orchestration is in `planning` until the first real `task_started` event, then stays in `implementation`; dispatch claims, conversation creation, `starting` state and plan selection do not cross that boundary.

Plan content is immutable after proposal. `active_plan_id` identifies the selected candidate, while `execution_plan_id` identifies the approved version that currently governs scheduling. Use `plan-propose` to submit a canonical candidate; the runtime derives `planning_revision`, `implementation_low_impact` or `implementation_high_impact`. Do not submit a self-declared change class. Planning revisions require a non-empty diff and fresh approval. Low-impact implementation revisions require a structured reason and are auto-approved. High-impact revisions require reason and evidence, keep the old execution pointer, hold only affected tasks and successors, and need `plan-approve` before scheduling under the new graph. Use `plan-abandon` to restore the old execution plan.

Never rewrite a started task's boundary or runtime identity in a plan payload. Use `task-migrate` with a new planned task ID, structured reason and evidence; the old task remains in the ledger as `superseded` with its facts and events. The dashboard and `view` projection keep phase, lifecycle, candidate/execution plans, revision diff and hold reasons separate. Do not infer completion from a candidate ID, `starting`, dispatch claim or a terminal plan label.

`examples/ledger-initialization/initial.json` is a synthetic, unapproved starting example, not an executable plan for a real project. Replace all example identities, dates and task details with verified facts before initialization. `examples/orchestration-viewer/ledger.ts` supplies a separate, richer synthetic dashboard example; see `examples/README.md` for the reproducible static preview and live demo.

Record the run identity in the conversation. Formal data lives only at `~/.local/share/multi-task-flow/data/runs/<run-id>/`. Development and tests require an explicit isolated profile and root. Conversation IDs and run IDs are distinct. If a fork's relationship or control is uncertain, stop before dispatch, cut or merge and ask the owner when that binding is needed. An owner transfer requires an explicit owner decision, verified prior conversation state, and no unresolved operations. Never claim a second main controller based on a copied ID alone.

Use `dispatch-group-claim` or `dispatch-claim`, then invoke `conversation-create` through this Skill’s CLI. The command binds the native request identity, creates and initializes the conversation through app-server, and resolves its real thread ID with the captured execution profile. An initial group/task thread ID is invalid, and an unknown result retains its claim and capacity; reconcile using actual native evidence before retrying, and ask the owner if the result cannot be established. Do not invent a thread ID or duplicate a creation. `task-update` records actual execution, waiting, blockers, and completion; `atom-update` records atoms sequentially. Ordinary blockers stay in the responsible conversation and ledger. Record key progress as a pending notification and deliver or acknowledge it using the permitted native communication tools; sent and acknowledged are distinct.

## 执行配置与 CLI 创建

运行只有一个完整的 `config.execution_profile = { model, thinking }`。交付单元和任务独立覆盖；未覆盖时各自使用运行默认值。新对象按 `kind-v1` 推荐表物化配置，手动修改后保持原值；`execution-profile-recommend` 只在主人显式要求重新推荐时执行。创建后的对话内调整属于会话运行时，不回写账本，也不主动重设。

使用 `execution-profile-update` 修改对象，payload 为 `{ target_type: "group" | "task", target_id, execution_profile: { model, thinking } | null }`；使用 `execution-profile-default-update` 修改默认值，payload 为 `{ execution_profile: { model, thinking } }`。所有写入带标准 owner/request/revision envelope，通过 app-server `model/list` 验证组合。认证网页复用相同 mutation contract，保留选择和 URL，并显示服务端错误。外部 source viewer 保持只读。

`conversation-create` payload 为 `{ operation_id, title, prompt }`，必须使用已获授权且尚未绑定 native request 的 dispatch claim。CLI 将完整 pair 传入 `thread/start` 的 `model` 与 `config.model_reasoning_effort`，校验服务端回传的 `model/reasoningEffort`，通过 `thread/name/set` 写标题，再用 `turn/start` 提交首条消息与 `effort`。CLI 保留连接直到初始化 turn 完成；超时或创建后的错误记录为 unknown，保留真实线程身份和 claim，必须对账后恢复，不得自动重建。任务 prompt 应先确认初始化并等待账本绑定，后续工作通过普通会话输入推进。

native request ID 一旦绑定，配置即冻结；明确失败且已对账的请求才允许修正配置并重新 claim。未绑定 native request 的 claim 遇到配置变化会终止旧 claim，审计记录保留旧 profile、原因和新 claim 要求。

旧账本缺少默认 profile 时保持只读。先完成原有 schema 迁移，再由绑定主会话显式调用 `execution-profile-migrate`，带 request ID、expected revision 和完整默认 pair。此操作保留账本上一快照，不推断旧对象的模型。历史 `create_thread` 证据可读；新增创建通过 CLI 证据解析。

## 主动通知闭环

记账命令可以在 `payload.notification` 中提供 `{ "mode": "auto" | "deliver" | "none", "recipient": "owner" | { "thread_id": "..." } }`。`auto` 保留各命令现有的默认通知规则，`deliver` 明确创建主动投递意图，`none` 禁止主动投递；旧字段 `notify_main: true` 继续等价于向 `owner` 投递。

通知创建与平台发送是两个阶段，但由同一个 CLI 命令完成闭环。记账命令先提交账本中的 `ledger_status: "committed"` 和 `delivery_status: "pending"`，随后 CLI 通过当前 Codex Agent API 的 `send_message_to_thread` 能力发送到 `recipient_thread_id`，再以 `notification-deliver` 写入真实的 `sent`、`failed` 或 `unknown` 结果。不得把写入 `pending` 报告为已通知，也不得把 `sent` 报告为收件人已读或已处理。

每次发送使用独立的 `delivery_attempt_id` 和平台证据。`request_id` 重放只返回原结果，不创建第二条通知或第二次尝试；明确 `failed` 可以在有界策略内以新的 `request_id` 重试。`unknown` 表示平台结果无法确定，必须先由 Agent 查询平台并以 `notification-reconcile` 写入 `reconciliation_id` 和查询证据，恢复器不得直接重复发送。在途发送持有通知专属文件锁，对账写入遇到 `NOTIFICATION_IN_FLIGHT` 必须等待该发送结束，不能将其改记 failed 以解锁第二次投递；进程终止后锁由操作系统释放，仍先查询平台再对账。只有 `recipient_thread_id` 对应的会话可以调用 `notification-ack`，发送方、`main` 或其他会话不得代为确认。

恢复时使用 `notification-reconcile --input -` 的无 `request_id` 形式查询 `pending`、`failed`、`unknown` 和长期未确认的 `sent` 通知；对 `pending` 或明确 `failed` 的通知使用 `notification-send --input -` 进行一次新的有界投递尝试；`unknown` 必须先对账，不能直接发送。CLI 通过 `CODEX_APP_SERVER_SOCKET`（默认检查 `$CODEX_HOME/app-server-control/app-server-control.sock`）连接 Codex app-server 的官方 Unix WebSocket 控制面，不伪造平台回执；若控制面不可用，则保留账本事实并记录 `failed`。

## PRs and cuts

Before **every** PR merge performed by a task or group Agent, use `merge-claim`; verify the actual PR identity, target, current head/base, applicable checks and task-owned quality proof using the bound Git provider, and respect the current authorization. A script input is an Agent's report, not independent provider evidence. After the external call, query the provider and use `merge-resolve` to record a matching receipt; if the result is uncertain use `unknown`, retain the occupation, and reconcile before any retry. Do not claim a failed operation from an unverified error. A task Agent owns its child PR quality proof and merge; the delivery coordinator owns only parent PR integration.

When a child PR has a conflict or failed checks, the task Agent must first determine whether its own changes caused the problem. Self-caused problems stay with the task Agent and must be fixed in the same task and PR. A confirmed external problem is escalated with diagnosis evidence, impact, and candidate orchestration changes to the main Agent; the main Agent asks the owner before creating a separate repair contribution task or changing dependencies. A changed base is always the task Agent's responsibility: rebase, revalidate, and refresh the task base evidence before retrying. Normal execution never transfers a task workspace or PR between Agents.

For an approved dynamic cut, `cut-claim` fences new merges and waits for prior occupations, then `cut-apply` records the current verified parent SHA and assignment changes atomically. Finished development work stays in the cut group; unfinished development subtasks move to the next default group with their existing conversations. The original group's release, deployment and verification tasks remain there and run after its parent PR merges. The next parent branch must include the actual previous parent merge before its development PRs merge. Follow PRs stay attributed to their original group; refresh its current SHA and review/check evidence when its branch advances, without changing cut ownership. An external provider `update-branch` that advances an established parent branch is recorded only through `group-base-reconcile` with matching previous/new SHA, branch, parent PR, provider and explicit update-branch evidence; it is not a merge or follow PR. The follow PR Agent notifies the main Agent, who coordinates needed rebases with affected unfinished task Agents.

A group closes only after its parent merge, CI on the merged SHA, planned post-merge tasks and known follow PRs complete. The main Agent may record `run-complete` only after all groups close and no operation or known follow PR remains unresolved. `resource-update` tracks each resource independently. Retain run data and any needed service until the owner confirms cleanup; resolve and clean only this run's exact resources.

## Dashboard

Use the installed user service through `bun --no-install run <skill>/scripts/service.ts <command> --input -`. Before viewer use, call `status`. If it reports `installed: false`, stop and guide the owner through approval: explain that installation writes the fixed user data root, reserves the configured loopback port, creates the user-level launchd service, and does not require administrator access; ask for explicit approval for this exact installation. Do not call `install` until that approval is received. After approval, build or select the verified bundle, show the exact source path, and call `install`; then call `ensure` with `{ "run_id": "<run-id>", "thread_id": "<main-thread-id>", "api_version": 1 }`. All projects and conversations share its stable `http://127.0.0.1:<configured-port>/runs/<run-id>/` entry. The CLI returns structured `ok/code/result`; `ensure` never builds, installs, upgrades or selects another port. Ordinary Agents may ensure, renew, release, inspect and obtain login entry points, but must not trigger installation, upgrade, rollback, credential maintenance or import without owner authorization. After `ensure`, call `login` and open its single-use URL using the Dashboard browser route when delivering or viewing a run.

The user-level launchd service owns the background lifecycle independently of conversations, requires no administrator access, and does not start at login. Independent main-thread/run leases last 60 minutes; related successful orchestration commands renew usage. Explicitly renew during long waits. Connected browser pages renew every 60 seconds with a five-minute TTL. Release only this run's Agent lease at closeout; never stop the shared service or release other runs' leases. The final expired lease triggers exit without deleting data. Next `ensure` recovers crashes. An unfinished ledger does not keep a process alive.

Use `login` with an optional `run_id` to obtain a single-use, 60-second browser entry. Treat that URL as a credential and do not put it into ordinary logs, ledgers or PRs. Stable run/plan links contain no credentials. Once logged in, `/` lists runs and `?plan=<plan-id>` selects a historical plan. The service validates Host/Origin and uses HttpOnly/SameSite browser sessions. For unavailable service links, call `ensure` first. Only currently subscribed runs hold filesystem watchers.

Per-run custom HTML/CSS/JS remains supported under `data/runs/<run-id>/view/`. Include `view.manifest.json` with `{ "api_version": 1, "frontend_contract": 1 }`. Missing or incompatible declarations preserve files and fall back to the shared template with a warning. Relative API/resource paths stay within `/runs/<run-id>/`; this is one same-user trust domain. Keep dependency graph, planned/actual timelines, group attribution, state, blockers, PRs, requirements and real conversation links. Conversation links use real IDs and canonical `codex://threads/<thread-id>` anchors.

For examples and external fixtures, use the generic read-only source-directory viewer. It accepts an absolute source run-data directory, validates its ledger and filesystem identity, assigns a random `view-<id>` presentation identity, and serves it through the same singleton. It reads the source in place, never publishes it under formal `data/runs`, never permits orchestration writes, and removes the mapping when its explicit browser view lease expires. Do not add an example-specific service mode or treat a source view as a real run.

`serve.ts` remains an internal synthetic/legacy validation helper, not the formal run entry or an upgrade fallback. The explicitly installed shared user service uses the system-service exception for its background lifecycle. See `references/shared-viewer.md` for fixed-port ownership, compatibility, maintenance and migration recovery.
